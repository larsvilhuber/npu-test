# Edge AI Showdown: Pi-like device with NPU vs. Intel N150 CPU: 3x faster than its integrated GPU, 12x faster than stock PyTorch

I never know what the purpose is of **NPU** (neural-processing unit). Turns out, I have an Orange Pi 5 sitting around, which actually does have one. Compared to a small computer running a low-power Intel CPU, that NPU can accelerate certain tasks, at lower power. But note that I did not have an "AI CPU" at hand, to compare what that would look like on an Intel chip that also has an NPU.

Now I need to figure out where I need this... (updating my [Birdnet Go](https://github.com/tphakala/birdnet-go) [node](https://app.birdweather.com/) on [Birdnet](https://birdnet.cornell.edu/)?)

> In a head-to-head [ResNet-18](https://docs.pytorch.org/vision/main/models/generated/torchvision.models.resnet18.html) inference benchmark, the **Orange Pi 5 (RK3588 NPU)** classified an image in **4.1 ms (246 images/s)** on one NPU core: **3.4x faster** than the Intel N150's integrated GPU, **7.7x faster** than its CPU running Intel's OpenVINO and **12x faster** than the CPU running stock PyTorch, while using about **a third of one CPU core** and staying over 30 °C cooler than the CPU runs. With all three NPU cores working on one image it took 2.6 ms (388 images/s). On a larger, video-style workload (YOLOv5s object detection at 640x640) the lead is smaller for a single stream (1.2-1.5x over the iGPU) and grows to about 3x with several streams.

All scripts, the raw CSV output of every run, and the code that produces the tables and graphs are in the [GitHub repository](https://github.com/larsvilhuber/npu-test).

| **GPU** | Mali GPU (`fb000000.gpu`, 300 MHz-1 GHz; Rockchip specifies a Mali-G610 MP4); not used here | Intel integrated GPU, 24 execution units, architecture 12.4.0, 0.2-1.0 GHz; used through OpenVINO |
| **Memory** | 15.6 GiB | 14.9 GiB |

The full tables, generated by the check scripts, are in the "System information" section at the end.

**The NPU driver version matters.** Rockchip's NPU driver is compiled into the kernel. The Orange Pi's stock vendor kernel (6.1.43) carries `rknpu` 0.9.3; the Ubuntu Rockchip 6.1.0-1026 kernel carries 0.9.7. All numbers below are from 0.9.7. On 0.9.3 only core 0 and the automatic core choice worked, jobs on cores 1 and 2 timed out and soft-reset the NPU, and two processes using the NPU at once crashed the kernel (a NULL pointer dereference in `rknpu_job_next` after repeated job timeouts), which hung the board. On 0.9.7 every core mask and concurrent processes work. See "Reproducing this" for how the newer kernel was booted.

## Benchmark Results Summary

ResNet-18, one 224x224 image per call, thousands of calls per test. I report the **median** latency: the Intel box also runs other services (see caveats), which adds a long upper tail to its means.

| System | Compute device | Runtime engine | Median latency (ms) | 95th pct (ms) | Throughput (img/s) | CPU busy (% of all cores) |
| :--- | :--- | :--- | ---: | ---: | ---: | ---: |
| **Orange Pi 5** | RK3588 NPU, automatic core | RKNN Lite 2 (v2.5.0), INT8 | **4.06** | 4.43 | **246** | 4.8 |
| **Orange Pi 5** | RK3588 NPU, core 0 pinned | RKNN Lite 2 (v2.5.0), INT8 | 4.09 | 4.50 | 245 | 4.7 |
| **Orange Pi 5** | RK3588 NPU, all 3 cores | RKNN Lite 2 (v2.5.0), INT8 | **2.58** | 2.99 | **388** | 7.1 |
| **Orange Pi 5** | 8 CPU cores (A76+A55) | PyTorch FP32 | 98.1 | 112.1 | 10.2 | 56 |
| **Intel N150** | 4 CPU cores | PyTorch FP32 | 48.9 | 417 | 20.5 | 95 |
| **Intel N150** | 4 CPU cores | OpenVINO FP32 | 31.4 | 61.3 | 31.9 | 92 |
| **Intel N150** | integrated GPU | OpenVINO FP32 | 14.0 | 14.9 | 71.7 | 46 * |

\* The N150 machine runs other services that use ~27% CPU on their own (see caveats), so the GPU run's CPU figure is mostly that, plus the driver thread.

Note that the NPU runs the model in INT8 (the pre-compiled model from Rockchip's examples), while all the Intel runs and the Orange Pi CPU run use FP32. Same network, different numeric precision; I did not check ResNet accuracy (for YOLOv5s below I compared detections).

### CPU and NPU usage

While the NPU runs inference, the Orange Pi's eight CPU cores are about 95% idle (4-5% busy overall, about a third of one core), and the NPU's busiest core sits at roughly 64-85% (sustained run: 85%). Doing the same work on the CPUs keeps the Orange Pi at 56% busy and the N150 at 95%.

![CPU vs NPU utilisation](https://raw.githubusercontent.com/larsvilhuber/npu-test/main/figures/utilisation.png)

### Five minutes of sustained load

Each engine also ran continuously for 300 seconds. Nothing throttles: the NPU stays at 4.4 ms and warms from 35 to 48 °C, the N150's iGPU holds 13.9 ms (71.7 img/s over 21,469 calls, with almost no spread: 95th percentile 14.7 ms), while the Orange Pi CPU run heats to 81 °C and the N150 CPU runs to 76-81 °C, with no visible drop in clock speed or throughput. (The N150's baseline is already ~68 °C because of the other services on that machine.)

![Sustained runs](https://raw.githubusercontent.com/larsvilhuber/npu-test/main/figures/sustained.png)

The OpenVINO-on-CPU run alternates between ~30 and ~48 ms in a regular rhythm of roughly ten seconds (38% of calls are above 45 ms), and the GPU panel shows a milder version of the same rhythm (temperature swings with it). I did not chase this down; the likely suspects are the other workload on the machine and the chip's power limits.

### Scaling on the CPUs

PyTorch on the N150 scales with threads (9.4 → 14.7 → 20.5 img/s at 1, 2, 4 threads); on the Orange Pi it barely does (7.6 → 10.2 img/s from 1 to 8 threads), because the big and little cores are very different. Batching helps both (N150: 20.5 → 27.1 img/s at batch 16).

![Thread and batch scaling](https://raw.githubusercontent.com/larsvilhuber/npu-test/main/figures/scaling.png)

### Scaling on the NPU's three cores

Two ways to use more than one core, measured with the stock ResNet-18 model and with the YOLOv5s model below. A single process can be given several cores (`core_mask` `0_1` or `0_1_2`), or several processes can each run on `NPU_CORE_AUTO`, which places each on an idle core.

| ResNet-18 | 1 | 2 | 3 |
| :--- | ---: | ---: | ---: |
| One process on N cores (img/s) | 245 | 339 | 388 |
| N processes (aggregate img/s) | 246 | 446 | 685 |

Splitting one image over cores gains little (1.6x for three cores), as Rockchip warns for small networks; separate processes scale nearly linearly (2.8x for three), with the per-image latency of each process staying near 4.2-4.5 ms. If the workload can be run as independent streams (several cameras or audio channels), that is the way to use the NPU.

![NPU scaling](https://raw.githubusercontent.com/larsvilhuber/npu-test/main/figures/npu_scaling.png)

## A video-style workload: YOLOv5s object detection

ResNet-18 at 224x224 is a toy next to what a camera pipeline runs, so I also ran [YOLOv5s](https://github.com/ultralytics/yolov5) at 640x640 with Rockchip's NPU-friendly ONNX export (`yolov5s_relu.onnx` from [`rknn_model_zoo`](https://github.com/airockchip/rknn_model_zoo), ReLU activations, sigmoids included in the graph, box decoding left to the CPU). The same ONNX file runs on every engine: OpenVINO FP32 on both Intel devices and the Orange Pi CPU, and RKNN INT8 (calibrated on 20 COCO images) and FP16 on the NPU. Two timings per engine: **model only**, and **end to end per frame**, which adds the letterbox resize, box decoding and non-maximum suppression (written in numpy, single-threaded, not tuned). The input is one decoded 640x640 frame; hardware video decoding and a real camera stream are not measured.

| System | Device, engine | Model only (ms / fps) | End to end (ms / fps) | CPU busy, end to end (%) |
| :--- | :--- | ---: | ---: | ---: |
| **Orange Pi 5** | NPU, INT8, one core | **27.2 / 36.8** | **41.1 / 24.3** | 12 |
| **Orange Pi 5** | NPU, INT8, all 3 cores | 21.4 / 46.7 | | |
| **Orange Pi 5** | NPU, FP16 | 55.9 / 17.9 | 69.5 / 14.4 | 10 |
| **Orange Pi 5** | 8 CPU cores, OpenVINO FP32 | 159.7 / 6.3 | 185.9 / 5.4 | 67 |
| **Intel N150** | iGPU, OpenVINO FP32 | 39.8 / 25.1 | 49.6 / 20.2 | 42 * |
| **Intel N150** | 4 CPU cores, OpenVINO FP32 | 152.1 / 6.6 | 164.9 / 6.1 | 83 |

For one stream the NPU is 1.5x ahead of the N150's iGPU on the model alone and 1.2x ahead end to end: much less than the 3.4x on ResNet-18, because decoding and NMS cost about 14 ms per frame on the Orange Pi's CPU cores (10 ms on the N150) and the NPU's single-core speed advantage shrinks on a larger network. FP16 on the NPU is about half the INT8 speed.

With several streams at once the picture changes (each stream is a separate process, 60 seconds, end to end):

| Concurrent streams | 1 | 2 | 3 | 4 |
| :--- | ---: | ---: | ---: | ---: |
| Orange Pi NPU, INT8 (aggregate fps) | 24.3 | 46.0 | 63.3 | 76.0 |
| N150 iGPU (aggregate fps) | 20.2 | 24.6 | 22.0 | 22.1 |
| N150 CPU (aggregate fps) | 6.1 | 5.0 | 5.2 | 5.2 |

The iGPU is saturated by one stream; the NPU keeps scaling until the Orange Pi's CPU (the post-processing) becomes the limit: at four streams the CPU is 45% busy and the NPU's busiest core 66%. Where several cameras share one box, the NPU's lead is about 3x at three streams. Moving the decoding and NMS off the CPU, or running them natively and not in numpy, would raise the NPU numbers further; I did not try.

Detections agree across engines on the sample photo (the model zoo's `bus.jpg`; four people and a bus): INT8 on the NPU found the same five objects as FP32 on the iGPU, with confidence scores within 0.012 and box corners within 2.2 pixels; FP16 and the CPU runs are within 0.008 and 0.7 pixels. One image is a sanity check, not an accuracy evaluation.

## A workload closer to Birdnet-Go: BirdNET audio classification

[Birdnet-Go](https://github.com/tphakala/birdnet-go) runs the BirdNET V2.4 TFLite model on 3-second, 48 kHz audio windows. I ran the very same FP32 model file that Birdnet-Go bundles (via TFLite/XNNPACK on the CPU) on both machines, with random noise as input (compute cost does not depend on the audio).

| System | Threads | Median per 3 s window (ms) | Real-time factor |
| :--- | ---: | ---: | ---: |
| Intel N150 | 1 | 50.8 | 59x |
| Intel N150 | 2 | 39.6 | 76x |
| Intel N150 | 4 | 41.1 | 73x |
| Orange Pi 5 (CPU) | 1 | 82.2 | 37x |
| Orange Pi 5 (CPU) | 4 | 53.4 | 56x |
| Orange Pi 5 (CPU) | 8 | 50.0 | 60x |

![BirdNET real-time factor](https://raw.githubusercontent.com/larsvilhuber/npu-test/main/figures/birdnet.png)

**Both machines are far faster than real time on the CPU alone**: even a single thread processes 37-59 seconds of audio per second. (On the N150 four threads are no faster than two; it is shared with other services.) A Birdnet-Go node listening to one or a few streams does not need an NPU for speed. I did **not** run BirdNET on the NPU. Two things stand in the way: the toolkit's TFLite loader exists only in the x86 build (the ARM64 build, which can run on the Orange Pi itself, converts PyTorch and ONNX models only), and BirdNET's graph computes its spectrograms inside the model with `RFFT2D` operators, which do not appear in Rockchip's supported-operator list. The case for the NPU on a bird node is therefore freeing CPU and energy, not speed, and it needs the spectrogram front end split off to the CPU.

## What did not work

- **The older NPU driver (0.9.3) is not usable for multi-core or concurrent work.** See the box under "The two machines". Rebuilding the model for multiple cores was not needed in the end: the stock ResNet-18 model, built with toolkit 2.3.2, runs on all core masks under driver 0.9.7.
- **Locking the NPU clock did not help.** I compared the NPU's devfreq governor set to `performance` against the default `rknpu_ondemand` and saw no meaningful change (4.46 vs 4.44 ms median sustained, 224 vs 225 img/s). I did not record the NPU clock during the runs, but it reports 1 GHz, the maximum the driver offers, so presumably the default governor already reaches it under load.

## Caveats

- The Intel N150 box (`oiseau`) is shared: it also runs Home Assistant, UniFi and other services, which use ~27% CPU and keep it at ~68 °C before my tests start. That inflates its tail latencies (note the 95th percentile of 417 ms for four-thread PyTorch against a 49 ms median) and could hide some of its true performance; the Orange Pi was idle. The GPU run is the least affected by it.
- The CPU governors differ: `performance` on the Orange Pi, `powersave` (intel_pstate, which still boosts to ~2.8 GHz under load) on the N150.
- I did not measure power, though lower power is the usual selling point of an NPU.
- INT8 (NPU) vs FP32 (everything else): not equal precision. The N150's iGPU could also run FP16 or INT8 models through OpenVINO; I used FP32 throughout, so the gap to the iGPU may be smaller against a quantized iGPU model. Accuracy was compared only on one image.
- YOLOv5s uses an NPU-friendly ReLU variant on all engines, not the stock SiLU model; the end-to-end timings include a deliberately simple numpy post-processing, and no video decoding.
- One run per configuration on one unit of each machine.

NPU load is read from `/sys/kernel/debug/rknpu/load`, and the NPU clock governor is set through `devfreq`; both need root, which I granted through two narrow sudoers rules (one exact file each) generated by [`scripts/sudoers/npu.sudoers.sh`](https://github.com/larsvilhuber/npu-test/blob/main/scripts/sudoers/npu.sudoers.sh).

The Orange Pi here boots from SPI U-Boot, which loads the kernel, initrd and device tree from the SD card's boot partition, with the root filesystem on NVMe. `boot-kernel.sh` copies the Ubuntu Rockchip kernel installed on the NVMe root into that partition (keeping the vendor files for `restore`). The NIC name changed with the new kernel (`end1`), so the network configuration needed adjusting.

## Key Takeaways

1. **Hardware acceleration matters:** the RK3588 NPU is an order of magnitude faster than either CPU for this vision task: 3.4x over the N150's integrated GPU, 7.7x over OpenVINO on its CPU, 12x over stock PyTorch, and 24x over the Orange Pi's own CPUs, on a single NPU core.
2. **Resource allocation:** inference on the NPU leaves the CPUs essentially free (about a third of one core for ResNet-18, about a tenth of the whole CPU for YOLOv5s end to end) and cool (about 40-48 °C vs 76-81 °C), which is where an always-on edge node benefits. The Orange Pi's own CPU is not THAT much slower than the N150 on audio ([see the CPU benchmark comparison](https://www.cpubenchmark.net/compare/6304vs4906/Intel-N150-vs-Rockchip-RK3588)).
3. **Software stack and the right silicon matter on the Intel side too:** switching the N150 from stock PyTorch to OpenVINO gave 1.6x on the CPU, and running the same OpenVINO model on the integrated GPU gave another 2.2x (3.5x over PyTorch), with very steady latency. That is the fair comparison for the NPU: it is still 3.4x faster, but a much smaller gap than against stock PyTorch. Whether the N150's GPU or the RK3588's NPU is cheaper in power I did not measure.
4. **For video-style work the NPU's advantage depends on concurrency:** on YOLOv5s a single stream is only 1.2-1.5x faster than the N150's iGPU, but the NPU scales across its three cores with separate processes (24 → 76 fps aggregate at four streams) while the iGPU does not scale at all (about 22 fps). The CPU-side post-processing becomes the next bottleneck.
5. **The NPU driver version decides what works:** on `rknpu` 0.9.3 only one core was usable and concurrent use crashed the kernel; on 0.9.7 all cores and concurrent processes work.
6. **For Birdnet-Go, speed is not the problem:** both CPUs run BirdNET 37-76x faster than real time. The NPU is attractive only if the model can be converted for it, to save CPU and power; I did not test that.
